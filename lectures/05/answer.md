## 宿題

- 取り組んだレベル：実装
- やったこと（変更したファイル・設定・処理、または設計した取得方法）：

  ベクトル検索に BM25（キーワード検索）を組み合わせ、2つの順位を RRF でまとめるハイブリッド検索を作った。以前 Colab で RAG を作ったときに使った方法を、このリポジトリに移植した形になる。

  BM25 は追加パッケージを使わずに書いた。日本語は2文字ずつ区切り、英数字は単語のまま扱う。ベクトル検索と BM25 からそれぞれ20件ずつ取り、RRF（k=60）で上位5件に絞る。`--hybrid` で切り替えられるようにし、ツール名・説明文・指示文は通常の検索と同じにした。検索の中身以外の条件を変えないためである。主な変更は `app/retrieval.py` で、テストも追加した。

- 比較した質問と、固定した条件（モデル・対象資料など）：モデルと対象資料は演習と同じ。質問は、演習の LoRA の質問、第3回のメモリの質問、QLoRA 論文の数値（48GB・650億）を聞く質問、「pytest はどんな場面の例として出てくるか」の4つ
- 結果（変更前後の回答・根拠、`--trace`の出力、時間・トークン数・生成API推定費用など）：

  はっきり差が出たのは pytest の質問だけだった。「pytest」と書かれているのは第3回 p.13 だけだが、このページは図が中心で、通常の検索では15位にとどまり取得できなかった。そのためモデルは、別ページのテストコードから推測して答えていた。ハイブリッドでは BM25 で1位になり、最終的に1位で取得できた。

  ```
  [tool call]   search_materials({'query': 'pytest'})
      - 第3回 p.13 メモリ [ベクトル 15位 / BM25 1位]
      - 第3回 p.7 LLMへの入出力 [ベクトル 1位 / BM25 圏外]
  ```

  残りの3問は、もともとベクトル検索で根拠がそろっていたので回答は変わらなかった。時間・トークン数・費用もほぼ同じだった（例：pytest の質問は 3.82秒 → 3.38秒、$0.00160 → $0.00141）。BM25 は API を呼ばないので、コストはほとんど増えない。

- 改善した例と、残る失敗・制約：

  改善したのは、固有名詞がそのまま本文にあるのに、意味の近さでは上位に来ないページを拾えるようになった点。

  実装中には、「RSI」で検索すると全ページがヒットするバグがあった。英数字も2文字ずつ区切っていたため、全ページのフッターにある「UNIVERSITY」に一致していた。英数字は単語のまま扱うように直した。

  残る弱点もある。RRF は両方の検索で上位にいるページを優遇するため、片方でしか上位に来ないページは落ちやすい。メモリの質問を質問文のまま検索すると、ベクトル検索では5位だった p.13 が上位5件から外れた。

- 気づき・疑問：

  BM25 の効き方は、モデルが作る検索語に大きく左右される。QLoRA の質問では、モデルが答えの数値を予想して検索語に入れていた。また今回は4問を1回ずつ試しただけなので、第4回のように評価セットを作り、上位5件に根拠ページが入る割合で比べないと、改善したとはっきりは言えないと思う。
